Starscream

Motion planning with a pretrained flight controller

Andrew Olvera

Starscream separates the choice of motion from the feedback control that executes it. A planner reads current physical state and upcoming gates, then chooses a continuous motion code. A pretrained controller turns that code into flight commands.

The method

Pretrain the parts, then learn to race

I start with physical representations and expert motion. A world model supplies the planner’s observation backbone; a separate motion encoder and controller learn an executable continuous interface from successful MPCC trajectories. JEPA-style alignment and physically propagated trajectory alignment connect the backbone to that interface. Racing PPO then improves the planner while the controller stays fixed.

01 Learn physical representations

An action-conditioned world model learns from closed-loop simulated flight. A compact Transformer encodes state, previous command, and two ordered gates. Autoregressive latent rollouts and physically scaled state-increment losses train representations of motion and actuation, including orientation and rotor dynamics.

02 Learn an executable motion interface

During privileged controller pretraining, an MLP compresses current ego49 and eight future motion samples over 0.4 seconds into a bounded continuous64 code. A feedback MLP combines that code with current ego49 and learns through PPO tracking rewards and reference-phase resets. The future samples enter through the encoder; they never bypass the code into the controller.

03 Align the observation-only planner

The privileged encoder becomes a frozen, stopped-gradient target. A Transformer initialized from the world-model backbone and a learned MLP projector predict the same 64D coordinates from current ego49 alone. A projector-only warmup precedes joint backbone updates.

Physical alignment then connects the planner to the frozen controller. Each 52-tick window starts at an expert state and proceeds on the system’s own achieved states, refreshing observations at every tick. Multistep position, velocity, rotation, angular-rate, and motor errors update the planner through the rollout. The expert trajectory supplies targets after initialization.

04 Optimize the planner for racing

Minibatch PPO refines the planner with progress, gate-passage, and collision rewards. A shared critic, two/four/full-gate curriculum, and learning-progress course sampler support training across layouts. The latest continuation retains 50% original seed-course lanes alongside gently augmented, geometrically qualified online variants. The low-level controller and motion interface stay frozen; final racing PPO uses no JEPA or dynamics auxiliary loss.

What the policy sees

ego49 = state19 + previous command4 + two gate13 descriptors. State19 contains body-frame gate-relative position, linear velocity, gate-to-body rotation, angular velocity, and four motor speeds. Each gate descriptor contains four ordered corner vectors and a validity mask.

The Transformer attends over state, previous-command, two gate, and readout tokens. This is token attention over the current observation, with no temporal observation history and no settings token. The projector is 128 → 256 → 64 with SiLU and a tanh output; the controller is 113 → 256 → 256 → 128 → 4. The actor has 220,352 planner parameters and 128,388 frozen controller parameters, plus four exploration parameters during training.

Simulation contract

A nominal lightweight racing plant

This version uses perfect simulator state and an exact gate map, with no observation noise or dynamics randomization. The plant is an engineering model of a lightweight five-inch racer, rather than identified Swift or A2RL competition hardware.
